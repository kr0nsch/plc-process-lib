# FB_SystemTime — системный источник времени

`FB_SystemTime IMPLEMENTS I_TimeSource` отдаёт монотонное время оператора `LTIME()`: наносекунды от
старта рантайма, 64 бит без знака (переполнение — через ≈ 584 года). Состояния нет, экземпляр
безопасен для любых задач. Каждый ФБ с входом `itfTime` держит свой экземпляр и берёт его, когда
`itfTime = 0`, — глобальных переменных времени в библиотеке нет.

Исходник: `src/POUs/Time/FB_SystemTime/`. Контракт: разделы 7.1, 7.2.

| Член | Сигнатура | Действие |
|---|---|---|
| метод | `Now : LTIME` | время этого вызова (`LTIME()`) |

Почему `LTIME()`, а не `TIME()`: `TIME` — 32 бит, мс, переполнение через ≈ 49,7 сут; объект работает
месяцами без перезагрузки, а мс мало для `dt` ПИД в задаче 1–2 мс. Справка CODESYS рекомендует
`LTIME()` вместо `SysTimeGetNs`; монотонность самого оператора в справке не описана.

**Реализация.** Оператор `LTIME()` стоит в инициализаторе локальной переменной метода `Now`, а не в
теле: локальные переменные метода инициализируются при каждом вызове, значение — время этого вызова
(тест `Time_SystemTime_IsMonotonic` проверяет, что время растёт от вызова к вызову). Причина —
iec_checker 0.4 не разбирает вызов `LTIME()` в теле (ParserError), а разбор входит в CI и в
pytest шаблона. Подробно — [STATIC_ANALYSIS.md](../STATIC_ANALYSIS.md).

**Проверить на объекте (R1, R16 контракта).** Монотонность при смене системного времени ОС и
разрешение `LTIME()` на ПЛК210 — ручной шаг [MANUAL_STEPS.md](../MANUAL_STEPS.md), раздел 9. Если
`LTIME()` поведёт себя иначе, замена локализована в `Now` (кандидат — `SysTimeCore.SysTimeGetNs`,
точную сигнатуру сверить в Library Manager).

## Пример

```st
VAR
    fbSysTime : PL.FB_SystemTime;
    ltNow     : LTIME;
END_VAR
ltNow := fbSysTime.Now();
```

## Тесты (`FB_Time_Test`)

`Time_SystemTime_IsMonotonic` — 20 000 вызовов: время не убывает, растёт и больше нуля;
`Delay_NoTimeSource_FallsBackToSystemTime` — `FB_Delay` без источника работает по системному времени.
