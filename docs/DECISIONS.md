# Решения по API: рассмотренные варианты и выбор

- Статус: принято 16.10.2026 для контракта [API.md](API.md) 1.0.0-rc2, действует для 1.0.0 (отличия — раздел 0 контракта). Документ объясняет, почему
  контракт устроен именно так: какие варианты сравнивались, что выбрано и почему.
- Основание: спецификация библиотеки (состав ФБ, требования к режимам, NE 107, NE 43, тестам и
  документации — [README](../README.md)), правила репозитория [CONTRIBUTING.md](../CONTRIBUTING.md),
  раскладка исходников [LAYOUT.md](LAYOUT.md); потребители — проекты портфолио 02 (КНС),
  07 (генератор кода iolistgen) и 10 (демонстрация ПАЗ).
- Сравнивались два варианта API:
  - **вариант A — эксплуатационный**: от пусконаладки и эксплуатации (что нужно оператору,
    наладчику, станционной логике и генератору);
  - **вариант B — объектный**: от архитектуры ООП (интерфейсы, шаблонный метод, отсутствие
    глобального состояния).
- Спорные языковые конструкции обоих вариантов проверены компиляционными зондами в CODESYS
  3.5.17.30 (раздел 6). Поведение во время выполнения позже проверили тесты на CODESYS Control
  Win V3 ([API.md](API.md#проверено-компиляцией-и-на-рантайме)).

## 1. Оценки

Шкала 1–5, где 5 — лучше. Оценки поставлены после компиляционных зондов: часть рисков
реализуемости ими снята.

| Критерий | A | B | Комментарий |
|---|---|---|---|
| Покрытие спецификации (раздел 2) | **5** | 4 | B: фильтр по неявному Эйлеру — реакция на ступень зависит от цикла, что нарушает требование «постоянная времени не зависит от цикла». Нет энергонезависимого режима, счётчики только у двигателя. A покрывает всё; отклонение A (LKG-конфигурация) задокументировано (A-01) |
| Удобство для HMI/SCADA | **5** | 3 | A: у всех устройств общий заголовок Cmd/Sts из 16-битных полей; результат команды `eCmdResult` + `uiCmdSeq`; слова `wFault`/`wWarning`/`wCfgErr` (видно, какой параметр неверен); маски тревог `wAlmActive`/`wAlmUnack`; квитирование и shelve масками. B: обратной связи по команде нет, ошибка конфигурации — один бит, Cmd лежит внутри экземпляра |
| Чистота ООП | 3 | **4** | B: нет глобальных переменных, встроенный запасной источник времени, шаблонный метод с хуками, разделённые интерфейсы, ПИД в общей иерархии. A: глобальный источник времени, расширение наследника через защищённые переменные, ПИД вне иерархии |
| Тестируемость | 4 | 4 | Оба: подменяемое время `FB_FakeTime`, тест за один вызов. A: выделенные `FB_StartsWindow` и тестовый приёмник событий. B: «время назад», функции без состояния (`F_RateLimit`), запасной источник времени |
| Удобство для генератора (07) | **4** | 3 | A: один массив тревог `astAlarm[]` одинаковой формы, `udiAlarmIdBase`, Cfg в Persistent Variables с инициализаторами в объявлении (идемпотентно). B: простые присваивания `inst.stCfg.x := …`, но программа инициализации при каждом старте ПЛК **затирает** уставки, изменённые оператором; приоритеты тревог собираются по-разному в каждом ФБ |
| Пригодность для КНС (02) | **5** | 3 | A: `xPowerOk` с паузой `tMinStop` против обратного вращения; `I_Motor` для чередования и АВР; `Available`/`ReadyToStart`; удержание значения AI на время подтверждения обрыва (нет ложного «сухого хода»); `xUseOutAct` для насыщения на минимальной частоте ПЧ; режим и OOS переживают перезапуск; журнал через `I_AlarmSink`. B: нет входа питания, нет `I_Motor`, режим после старта — из `eModeInit` |
| Пригодность для ПАЗ-демо (10) | 4 | 4 | Оба отдают наружу `I_TimeSource`, `FB_FakeTime`, `FB_Delay`, `FB_Alarm`. A явно ограничивает переиспользование; у B есть выходы «осталось времени» и «время назад» |
| Реализуемость в CODESYS 3.5.17.30 | 4 | 4 | Зонды подтвердили конструкции обоих вариантов: `LTIME()`, `VAR_IN_OUT CONSTANT`, `ABSTRACT`, `STRUCT EXTENDS`, индексацию перечислением, инициализацию массивов структур. У A остаётся правило «методы не трогают `VAR_IN_OUT`» (соблюдается копией LKG). У B — запись в `VAR_INPUT` изнутри ФБ и `REFERENCE TO` во входе |
| Простота | 3 | **4** | A: больше механизмов (окно сброса, LKG, импульсная схема пуска). B компактнее |
| **Итого (из 45)** | **37** | **33** | |

**Выбор:** основа — **A**. Из B взяты идеи, которые делают A чище, не ломая эксплуатационную
логику (раздел 3).

## 4. Что оставлено от варианта A и почему

| № | Решение A | Альтернатива B | Почему A |
|---|---|---|---|
| D-01 | `stCmd` — `VAR_IN_OUT` на структуру в `GVL_Hmi` приложения. ФБ сам сбрасывает импульсные биты прямо в памяти HMI/SCADA | `stCmd` во `VAR_INPUT` экземпляра | HMI видит квитирование команды (бит сброшен, `uiCmdSeq` вырос) в той же переменной, в которую писал. Слежение (`rSpeedSp_pct := текущее`) тоже видно сразу |
| D-02 | `stCfg` — `VAR_IN_OUT CONSTANT`, Cfg хранится в Persistent Variables приложения | `stCfg` во `VAR_INPUT`, инициализация программой при старте | Уставки оператора переживают перезагрузку и загрузку программы; нет копирования на входе; ФБ не может испортить Cfg. Зонд P6: `VAR_IN_OUT CONSTANT` компилируется |
| D-03 | Энергонезависимые данные — `ST_DeviceRetain` (`VAR_IN_OUT`) в объекте Persistent Variables приложения. В библиотеке нет ни одной RETAIN/PERSISTENT-переменной | `REFERENCE TO ST_MotorCounters`, `REF=` каждый цикл | Одна структура на все типы, режим и OOS тоже энергонезависимы. Зонд P18: `PERSISTENT` в обычной GVL и в ФБ даёт предупреждение C0244, нужен объект Persistent Variables — значит, это решение приложения, а не библиотеки |
| D-04 | Общие части Cmd/Sts — вложенная `stCommon` | `STRUCT EXTENDS` | Методы базы принимают `stCmd.stCommon` как `VAR_IN_OUT ST_DeviceCmd` — без приведения типов. В SCADA общий заголовок — отдельный тип. Зонд P7 показал, что `STRUCT EXTENDS` тоже работает, но плоский путь не стоит второго механизма |
| D-05 | Обратная связь по команде `eCmdResult` + `uiCmdSeq`; `wFault`/`wWarning`/`wCfgErr` в общем заголовке | — | Оператор видит «отклонено: блокировка», наладчик — какой параметр неверен |
| D-06 | Режим и OOS энергонезависимы (`stRetain.eRemoteMode`, `xOutOfService`) | `eModeInit` из Cfg | Насос, выведенный в ремонт, не «оживает» после перезагрузки; КНС после провала питания продолжает в Auto |
| D-07 | Неверная Cfg **при старте** → CheckFunction + безопасный выход (буквально по спецификации). Неверная Cfg **в работе** → CheckFunction и биты `wCfgErr`, логика продолжает по последней корректной копии (LKG) | Каждый цикл: безопасный выход | Запись многополевой уставки с HMI/SCADA не атомарна. Промежуточная комбинация, например `rRangeLo > rRangeHi` между двумя записями, при подходе B на цикл останавливает работающий насос. Так же ведут себя блоки РСУ: недопустимое изменение параметра отклоняется, работает старое значение. Отклонение от буквы спецификации записано в [ASSUMPTIONS.md](ASSUMPTIONS.md) (A-01) |
| D-08 | Механические отказы фиксируются до Reset; отказы сигнала и связи — нет (тревога остаётся `RtnUnack`) | Опции `xDriveFaultLatch`, `wInterlockLatchMask` | Меньше параметров. Фиксация блокировок — задача станции или ПАЗ |
| D-09 | `xPowerOk`, окно сброса `tResetWindow` и импульс `xQReset` для УПП/ПЧ | — | Без этого насосы КНС после провала напряжения «залипают» в аварии |
| D-10 | 8 слотов `FB_Alarm` в базе, индекс — перечисление типа, `udiId = udiAlarmIdBase + слот`, Cfg тревог — `astAlarm[0..7]` в каждой Cfg | Массив своего размера в каждом ФБ, Cfg тревог собирается из разных полей | Одна форма для генератора и SCADA (`astAlarm[i].ePriority`); «квитировать всё» и маски — один цикл в базе. Зонды P8–P10: индексация нестрогим перечислением и частичная инициализация массива структур компилируются |
| D-11 | Push-события `I_AlarmSink` через `GVL_Lib.itfAlarmSink` (единственная изменяемая глобальная переменная библиотеки) | Опрос `Seq` по массиву `I_AlarmSource` | Журнал КНС на 200 записей не теряет переходы, случившиеся за один цикл. Опрос через `Seq` тоже остаётся (G12) |
| D-12 | AI: удержание последнего хорошего значения на время подтверждения отказа; при подтверждённом отказе флаги уставок FALSE, тревоги уставок подавлены. Опция `xLimitsOnFail` — считать уставки по `rFailValue_eu` (идея B) | Уставки всегда по значению отказа | Для КНС отказ уровнемера — деградированный режим по поплавкам, а не ложный «сухой ход». Для объектов, где отказ = срабатывание, есть опция |
| D-13 | Обратный расчёт ПИД по фактическому выходу `rOutAct_pct` (`xUseOutAct`) | Только слежение `xTrack` | Внешнее насыщение (минимальная частота ПЧ) при Auto видит только фактический выход; `xTrack` — для механизма не в Auto |

## 6. Факты компиляционных зондов

CODESYS 3.5.17.30, Control Win V3 32 бит, 16.10.2026. «Компилируется» значит: 0 ошибок и
0 предупреждений, если не сказано иное. Каждый вопрос проверялся в отдельном чистом проекте:
ошибки одного объекта маскируют проверки в других, поэтому три вывода первого прогона (P5 в части
тела, P14, P15) пересмотрены зондами Q (таблица ниже и
[API.md](API.md#проверено-компиляцией-и-на-рантайме)).

| № | Конструкция | Итог |
|---|---|---|
| P1 | Оператор `LTIME()` в методе `Now : LTIME` | компилируется |
| P2 | `LTIME_TO_ULINT(LTIME#1S) / 1000000000` в границе массива = 1 → единица `LTIME` — нс | подтверждено вычислением константы компилятором |
| P3 | `TIME_TO_UDINT(T#1S) / 1000` = 1 → `TIME` в мс | подтверждено |
| P4 | `FUNCTION_BLOCK ABSTRACT`, `METHOD PROTECTED ABSTRACT`; экземпляр абстрактного ФБ | компилируется; экземпляр — ошибка 434 «имеет тип ABSTRACT и не может получить экземпляр» |
| P5 | `SUPER^.Method()` в переопределённом методе, `THIS^.Method()` в теле базы | компилируется. **Вызов тела базы `SUPER^();` без `VAR_IN_OUT` базы — ошибка C0039 (Q1)**; с явной передачей всех `VAR_IN_OUT` — компилируется (Q3) |
| P6 | `VAR_IN_OUT CONSTANT` в ФБ и в параметрах метода | компилируется |
| P7 | `STRUCT EXTENDS`; передача производной структуры в `VAR_IN_OUT` базового типа | компилируется |
| P8 | Нестрогое перечисление `... ) UINT;` как индекс массива | компилируется |
| P9 | `GVL_Const.DEV_ALARMS_MAX - 1` (`qualified_only`) в границе массива внутри DUT | компилируется |
| P10 | Частичная инициализация массива структур `[(ePriority := ...), ...]` и повтор `7((...))` | компилируется |
| P11 | `INTERFACE I_X` без `__System.IQueryInterface`, цепочка `EXTENDS`, `itf <> 0`, `GetAlarm := 0`, `ARRAY OF I_Motor`, элемент массива ФБ как результат типа интерфейса | компилируется |
| P12 | Глобальная переменная-интерфейс в GVL с `qualified_only` | компилируется |
| P13 | `SHL(WORD#1, ui)`, битовый доступ `w.15 := x`, `MAX` строгих перечислений, `EXP` на LREAL | компилируется |
| P14 | Вызов ФБ без `VAR_IN_OUT` после вызова с ними | **ошибка C0039 (Q2)**: все `VAR_IN_OUT` передаются в каждом вызове (правило R1 контракта) |
| P15 | Чтение `VAR_IN_OUT` ФБ из метода | **предупреждение C0371 (Q5)**; сборка библиотеки считает его ошибкой (правило R2) |
| P16 | Строгое перечисление: `eMode := 2;` (значение есть в перечислении) | **компилируется** → защита от 0 и мусора нужна во время выполнения (санитизация) |
| P17 | `SIZEOF(ST_DeviceRetain)` (раскладка API) | = **36** байт на Control Win V3 32 бит |
| P18 | `VAR_GLOBAL PERSISTENT RETAIN` в обычной GVL; `VAR PERSISTENT` в ФБ | предупреждение C0244 «Приложение не содержит VAR_PERSISTENT-списка…» → нужен объект Persistent Variables |
| P19 | Идентификатор `r` (`r : REAL;`) | ошибка разбора: `R` зарезервирован (оператор IL); `st`, `s`, `ld` — тоже (Q13), `n` — нет |

## 7. Решения, принятые при реализации

Решения, которые контракт не задаёт или от которых реализация отступает, вместе с проверкой —
в [ASSUMPTIONS.md](ASSUMPTIONS.md) (записи F-01…). Главные из них:

| № | Решение | Почему |
|---|---|---|
| F-01 | Наборы тестов регистрируются из GVL семейства с `{attribute 'linkalways'}`, `PRG_Tests` только вызывает `coUnit.RUN()` | Команды семейств пишут тесты параллельно, не правя общих файлов. Без `linkalways` набор молча пропадает (зонд на рантайме) |
| F-03 | Компиляционное покрытие даёт тестовая сборка | CODESYS 3.5.17 компилирует только объекты, достижимые из задач: каждый публичный объект должен быть достижим из тестов |
| F-07, F-18 | Границы массивов в секциях переменных были числом с тестом совпадения с константой — **снято**: граница — константа | Статанализатор iec_checker 0.4 не разбирал константы в границах массивов; понижение шаблона теперь подставляет их значения |
| F-17 | Свойство приоритета тревоги — `AlarmPriority` вместо `Priority`, закреплено в контракте 1.0.0 | `PRIORITY` — ключевое слово МЭК 61131-3 (объявление задачи `TASK`): член публичного API с таким именем непереносим. Найдено разборщиком iec_checker 0.4 |
| F-26 | Базу проверяет тестовое устройство `FB_TestDevice`, а не устройства библиотеки | Устройства пишутся после базы; тестовое устройство — рабочий образец порядка тела для команд |
